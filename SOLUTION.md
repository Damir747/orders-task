# Решение тестового задания

## 1. Что сделано и какие решения приняты

### 1.1. Поддержка скидок в дневной статистике

Добавлена поддержка финансовых полей `discountPercent` и `amountPaid`.

Для каждого дня статистика рассчитывается по оплаченным заказам:

- `gross` — сумма заказов до скидок;
- `net` — фактически уплаченная сумма (`amountPaid`);
- `discount` — разница между `gross` и `net`;
- `total` — сохранено для обратной совместимости и равно `gross`.

Все денежные значения внутри приложения хранятся в целых копейках. В API суммы возвращаются в рублях с точностью до копейки.

Для хранения новых данных добавлена миграция `002_order_payment_amounts.sql`:

- `amount_paid_kop` — фактически уплаченная сумма;
- `discount_percent` — процент скидки.

Для существующих записей выполнено заполнение новых полей: `amount_paid_kop` принимается равным `amount_kop`, а `discount_percent` — равным нулю. Это допущение связано с тем, что исторические суммы после скидок отсутствовали в прежней схеме.

### 1.2. Точность денежных вычислений

Устранены проблемы, связанные с погрешностями арифметики JavaScript `Number` при переводе рублей в копейки.

Реализовано преобразование через десятичное представление значения и `BigInt`. Проверяются корректность формата, отсутствие дробной части меньше копейки и безопасный диапазон целых значений.

Это позволяет корректно обрабатывать значения вроде `1.15` и `0.29`, не полагаясь на потенциально неточное умножение числа с плавающей точкой на 100.

### 1.3. Исправление расчёта дневной статистики с учётом таймзоны

Причина расхождения заключалась в вычислении смещения таймзоны клиента один раз — относительно текущей даты — с последующим использованием этого смещения для всех заказов.

Такой подход некорректен для исторических данных, поскольку смещение IANA-таймзоны может меняться в зависимости от даты, например при переходе между стандартным и летним временем (DST).

Исправление: локальная календарная дата теперь определяется отдельно для каждого заказа с использованием `Intl.DateTimeFormat` и таймзоны клиента. Форматтер создаётся один раз на запрос и используется для обработки всех заказов.

Добавлены тесты для:

- дат до и после перехода на летнее время в Берлине;
- заказов около полуночи UTC;
- исторических зимних дат;
- включительных границ запрошенного периода.

### 1.4. Защита от конкурентных обновлений заказов

Ранее проверка версии заказа и его сохранение выполнялись отдельными операциями. При параллельной обработке синхронизации и вебхука более старая версия могла перезаписать новую.

Обработка обновления переведена в транзакцию с использованием PostgreSQL advisory transaction lock по идентификатору заказа.

Внутри транзакции:

1. Блокируется обработка конкретного заказа.
2. Читается текущая версия `updated_at`.
3. Если входящая версия не новее сохранённой, изменение признаётся устаревшим.
4. Если входящая версия новее, заказ обновляется.
5. Если заказа ещё нет, он создаётся.

Это обеспечивает согласованную обработку параллельных обновлений, в том числе при одновременном первом создании заказа.

Синхронизация и вебхуки используют общий механизм применения заказа.

### 1.5. Надёжность пагинации

Добавлена проверка структуры ответа внешнего API и значения `nextCursor`.

Обработка синхронизации учитывает:

- нормальное завершение при `nextCursor: null`;
- пустую страницу с тем же курсором;
- пустую страницу с новым курсором;
- повторяющиеся курсоры и циклы пагинации;
- ограничение максимального количества страниц.

Это предотвращает бесконечную обработку и незаметное усечение синхронизации при некорректном ответе внешнего API.

### 1.6. Обработка HTTP-ошибок

Улучшена нормализация ошибок HTTP:

- ошибки некорректного клиентского запроса возвращают соответствующие HTTP-статусы;
- некорректный JSON от внешнего API обрабатывается как ошибка upstream;
- внутренние ошибки не раскрывают клиенту подробности реализации;
- неизвестные маршруты возвращают согласованный формат ошибки;
- диагностическая информация остаётся доступной во внутренних логах и данных запусков синхронизации.

## 2. Причина расхождения из жалобы аналитиков и как она была найдена

В исходной реализации дневной статистики смещение таймзоны клиента вычислялось относительно текущей даты и затем применялось ко всем заказам.

Это приводило к ошибкам при обработке исторических дат в таймзонах с переходом на летнее время.

Смещение таймзоны не является постоянным свойством клиента: оно зависит от конкретной даты. Поэтому применение текущего смещения к историческим заказам могло сдвигать их локальную календарную дату и относить сумму к соседнему дню.

Проблема была выявлена при анализе реализации расчёта дневных итогов и проверке поведения на исторических датах, включая переходы DST.

Исправление заключается в определении локальной календарной даты отдельно для каждого заказа с использованием его временной метки и IANA-таймзоны клиента.

Добавлены регрессионные тесты для исторических дат, переходов DST и границ суток.

## 3. Дополнительные наблюдения

### 3.1. Невалидные записи при синхронизации

Во время итогового запуска синхронизации получен следующий результат:

| Показатель       | Значение |
| ---------------- | -------: |
| Страниц          |       52 |
| Получено записей |     5030 |
| Применено        |     3853 |
| Невалидных       |     1177 |
| Устаревших       |        0 |

Счётчик `invalid` увеличивается, когда проверка схемы заказа или его нормализация завершается `ValidationError`.

Возможные причины включают отсутствие или некорректность обязательных полей, неподдерживаемый статус, некорректные денежные значения и даты.

Текущая диагностика сохраняет агрегированное количество отклонённых записей, но не сохраняет идентификаторы отдельных заказов и подробности ошибок валидации. Поэтому установить точное распределение 1177 отклонений по причинам на основании результата запуска невозможно.

Я не связываю эти отклонения с конкретными полями внешнего API без подтверждающих данных.

Невалидные записи пропускаются, остальные заказы продолжают обрабатываться.

### 3.2. Длительность синхронизации

Полный запуск синхронизации занял около девяти минут. Внешний API вернул 5030 записей за 52 страницы.

Это показывает, что полный сценарий синхронизации на предоставленном наборе данных может выполняться достаточно долго. В дальнейшем имеет смысл отдельно исследовать производительность запросов к внешнему API и сохранения заказов.

### 3.3. Вебхуки

После синхронизации был выполнен предусмотренный README сценарий отправки вебхуков.

Отправлено 92 вебхука, все 92 запроса получили HTTP 200.

Обработка вебхуков и синхронизация используют общую бизнес-логику применения заказа с проверкой `updatedAt`. Это позволяет защищать данные от повторных и устаревших обновлений независимо от источника поступления заказа.

## 4. Принятые допущения

1. Для существующих заказов, у которых до миграции не было данных о фактически уплаченной сумме, `amount_paid_kop` заполняется значением `amount_kop`, а `discount_percent` — нулём. Исторические скидки невозможно достоверно восстановить из старых данных.
2. Денежные значения хранятся в копейках. Значения, содержащие ненулевую долю копейки, считаются некорректными и отклоняются.
3. При равенстве `updatedAt` входящая версия считается устаревшей. Это предотвращает повторное применение события с тем же временем изменения.
4. Даты в статистике определяются по календарной дате в таймзоне клиента, а не по UTC-дате и не по текущему смещению таймзоны.
5. При обработке синхронизации невалидные отдельные заказы пропускаются с увеличением счётчика `invalid`, а ошибка всей синхронизации резервируется для ошибок, препятствующих продолжению запуска.

## 6. Что можно улучшить при наличии дополнительного времени

1. Добавить подробную диагностику невалидных заказов: идентификатор заказа, поле и причина отклонения, с ограничением объёма и без сохранения чувствительных данных.
2. Исследовать причины большого количества невалидных записей на полном наборе данных mock API.
3. Профилировать длительную синхронизацию и определить возможности оптимизации сетевых запросов и записи в базу.
4. Добавить метрики длительности обработки страниц, количества ошибок валидации и времени сохранения заказов.
5. Расширить интеграционные проверки полного сценария синхронизации и вебхуков.
